PART 1 — 公式仕様（全て一次資料で裏取り済み）

設計の6本柱

① エージェント＝「ペルソナ単位の完全スコープ」

OpenClaw の「エージェント」は workspace・auth・モデル設定・セッションストアを束ねた単位で、agents.list により1つの Gateway プロセス内に複数の分離エージェントを走らせられます。各エージェントは自動的に独立 workspace（独自の AGENTS.md / メモリ）を持ち、モデル・skills 許可・名前/アバターも個別に設定可能。

docs.openclaw.ai/concepts/multi-agent ・ /gateway/config-agents ・ /concepts/agent-workspace

⚠️ 注意2点：agentDir の使い回しは厳禁（auth/セッション衝突。公式が明示警告）。「分離」はセキュリティサンドボックスではなく状態の分離（絶対パスを書けばホストに届く）。

② bindings：チャンネル→エージェントの決定論的ルーティング

bindings 配列が Discord bot アカウントをエージェントにマッピングします。解決は「最も具体的なものが勝つ」9段階の固定優先順位（exact peer → スレッド親 → guild+ロール → guild → アカウント → デフォルト）。つまり「このチャンネルはこのエージェント」を設定で確定的に固定できます。

openclaw bindings add --agent blog --channel discord --account fourth

docs.openclaw.ai/channels/channel-routing ・ /concepts/multi-agent

③ エージェント間メッセージング（sessions_send）は既定OFF

司令塔がエージェント間で指示・報告をやりとりする公式手段は sessions_send。ただし既定で無効で、tools.agentToAgent に enabled: true＋許可エージェントIDの列挙が必要です。

{ "tools": { "agentToAgent": { "enabled": true,
    "allow": ["main", "blog", "video", "engineer"] } } }

docs.openclaw.ai/concepts/multi-agent ・ /tools/multi-agent-sandbox-tools

④ sessions_spawn：公式オーケストレータ・パターン

サブエージェント起動は非ブロッキングで即 run id を返し、隔離セッションで走ります。maxSpawnDepth: 2（公式推奨値）で「main → オーケストレータ → ワーカー」の階層が組め、結果は下から上へ自動集約。既定値：同時実行 8・子エージェント上限 5。重い/反復タスクのサブエージェントには安価なモデルを割り当てるのが公式推奨（サブ側だけ Sonnet 等に落とす＝コスト設計がそのまま公式に載っている）。

docs.openclaw.ai/tools/subagents（v2026.2.15 出荷）

⑤ Task Flow：複数ステップ制作の「耐久レコード」

Task Flow はバックグラウンドタスクの上位レイヤで、複数ステップ作業の状態（status・JSON state・リビジョン）を Gateway 再起動をまたいで保持します。公式は定期ワークフローを4層に分離することを推奨：①タイミング＝cron ②文脈継続＝persistent cron session ③決定的ステップ・承認ゲート＝Lobster ④進捗追跡＝Task Flow。管理は openclaw tasks flow list|show|cancel。

docs.openclaw.ai/automation/taskflow ・ /automation（2026.4.2 出荷の新機能）

⑥ cron vs heartbeat の公式基準

「正確なタイミング・隔離実行なら cron／フルのセッション文脈が効いて時刻が概算でよければ heartbeat（既定30分）」。cron は必ずタスクレコードを残し、heartbeat は残しません。脚注：Anthropic OAuth 認証だと heartbeat 既定が1時間になるため、使うなら heartbeat.every を明示設定。

docs.openclaw.ai/automation#scheduled-tasks-cron-vs-heartbeat ・ /gateway/heartbeat

CRITICAL FINDING

⚠️ 今の構成に直接効く発見：botはDiscordメンションで会話できない

GitHub Issue #11199（コミュニティ報告・実装確認あり）：OpenClaw は自インスタンスに設定された全botアカウントからの受信メッセージをフィルタします。つまり Claw02 が #総合管理 に報告を投稿しても、main bot はそれを「読んで」いません。

今の「部下bot→総合管理チャンネルへ完了報告」はsenao が読む分には機能していますが、司令塔botによる自動統括（報告を受けて次の指示を出す）は Discord 経由では成立しないということです。bot同士の連携をやるなら ③ の sessions_send（＝agents.list 分離が前提）が唯一の公式ルートです。

関連して、各チャンネルセッションは設計上互いに見えない（同一エージェントでもチャンネル間のクロス認識なし）、MEMORY.md の自動ロードはDMセッションのみ（ギルドチャンネルではメモリツールを明示的に使う必要）も公式仕様として確認しました。

github.com/openclaw/openclaw/issues/11199 ・ docs.openclaw.ai/channels/discord

senao 構成への適用設計図（段階移行）

一気に分離せず、混線・容量の実害が出ているところから段階導入するのが妥当です（エージェント数×独立コンテキスト分のトークン・メモリ増があるため。Mac mini 16GB）。

現状維持でよいもの

軽い担当（リサーチ・運用戦略・広報など）は今の「main＋ペルソナ切替」のままで問題なし。並行性はチャンネル数で既に確保済み（本日実測：並行2本=9秒 vs 直列20秒）。

1

制作系だけ agents.list で独立エージェント化

ブログ・動画編集・エンジニア×2 を独立エージェントに分離 → bindings でチャンネルに固定。効果は3つ：

  • メモリ・セッション・skills 許可がチャンネル毎に分離（制作物の文脈が混ざらない）
  • AGENTS.md の肥大が解消——今日21,630字で上限90%に達している単一ファイルが、エージェント別の小さなファイルに分割される（切り捨てリスクの恒久解決）
  • エージェント別にモデルを変えられる（制作系だけ強いモデル、など）
2

司令塔の統括を「本物」にする

tools.agentToAgent を有効化して main→専門エージェントの指示・報告を sessions_send で配線（Discord経由のbot間会話は不成立のため、これが唯一の公式ルート）。エージェント内の並列作業は maxSpawnDepth: 2＋サブエージェントに安価モデル割当でコストを抑える。

3

制作パイプラインを Task Flow に載せる

「日次リサーチ→記事化→サムネ→承認→公開」のような複数ステップは、cron（時刻）＋Task Flow（再起動耐性のある進捗追跡）＋Lobster（承認ゲート）に分離。既存の Discord ✅/❌ PreToolUse ゲートと役割が重なるため、統合方法は次の調査課題。運用の観測は openclaw tasks list / audit をループに組み込む。

※ この設計図の「事実部分」は全て3-0で検証済みの公式docs由来。「senao 環境でこう組むべき」という適用判断はリサーチからの推論であり、docs が直接この構成を推奨しているわけではありません。
