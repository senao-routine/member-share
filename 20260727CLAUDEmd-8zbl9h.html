CLAUDE.md の棚卸し
何を消し、何を残し、何を移すか

Claude Opus 5 の公式ガイドは「検証の指示は削除しなさい」と書いています。では自分の設定ファイルの、どの行を消せばいいのか。判断基準と、事故らせない手順をまとめました。

2026-07-27 ／ 日曜セミナー 第04回の資料

CLAUDE.md は「お願い」であって「鍵」ではない。
だから削除の是非は、その1行が消えたら誰が止めるのか、だけで決まる。

SECTION 01

まず、公式コマンドがあります

手の内を先に明かします。/checkup（/doctor でも同じ）という公式コマンドが 2026年7月8日にリリースされています。点検項目の中に「肥大化した CLAUDE.md をネストした CLAUDE.md とスキルに分割する」が入っていて、しかも変更前に1件ずつ確認を取ってくれます。

まずはこれを回してください。ただし——出てきた提案をそのまま全部適用してはいけません。

SECTION 02

「短くなりました」を信じた結果

2026年7月14日に公開された実体験の記録があります。Claude に「冗長な項目を削除して200行以内にして」と依頼したところ、「215行を71行に、約3分の1に圧縮しました」と報告が返ってきた。中身を目視確認せずに信用したそうです。

1ヶ月半後にファイルを開いたら、Claude は勝手に「1項目1行＋参照ファイルへのリンク」形式に変えていて、そのリンク先に143ファイル・数百行分が隠れていました。本体は短いのに、総量は何倍にも膨らんでいた。コンテキストを圧迫していたのは、むしろ整理した後だったわけです。

研究でも同じ結果が出ています

ICLR 2026 に出ている ACE という研究が、AIに蓄積した文脈を丸ごと書き直させたときの挙動を実測しています。

状態トークン精度
元の文脈18,28266.7
何も手を加えない—63.7
1回リライトした後12257.1

整理した結果、何もしないより悪くなっています。論文の処方箋も明快で、「全体をリライトするな、増分で更新しろ」。

SECTION 03

なぜ、書いても守られないのか

根本原因は公式ドキュメントにはっきり書かれています。

CLAUDE.md は文脈であって、強制設定ではない。システムプロンプトですらなく、その後にユーザーメッセージとして渡されています。読んで従おうとはするけれど、厳密に守る保証はない。そして止めたいなら PreToolUse hook を使え、とまで書いてあります。

だから冒頭の一行に戻ります。お願いであって、鍵ではない。

SECTION 04

4分類 — その1行は、どれに当たるか

分類中身の例判定
Aコードやファイルを読めば分かるディレクトリ構成／依存一覧／アーキテクチャ概説消してよい
Bリンタ・テスト・型が既に強制インデント幅／フォーマット規約消してよい
Chook・permissions が既に強制破壊的コマンドの禁止／公開前の検査消してよい（移設先を記録）
D誰も機械的に強制していない環境固有の事実／変更禁止の固有名／バージョン固定／公開ポリシー消さない

誰も止めないなら、消さない。何かが止めるなら、消してよい。

迷ったときの3つの問い

  1. これを消したら、AIがミスをするか？ — しないなら切ってよい（公式ベストプラクティスの原文）
  2. これはAIがファイルを読んで再発見できるか？ — できるなら A
  3. 今それを守っているのは、文章か、それとも仕組みか — 文章だけなら D

D は「消えても、その場では何も起きない」

バージョン固定、実行環境の癖、変更禁止の固有名。AIから見ると「もう使われていなさそう」に見える行です。しかも壊れるのは、次に実際に使ったとき。削除の瞬間には何も起きないので、原因にたどり着けません。

SECTION 05

公式の「書く／書かない」対照表

削る動機そのものは正しいことも、公式が保証しています。

各行に対してこう問え、と書かれています。「これを消したら Claude がミスをするか？」しないなら切れ。そして肥大化すると、書いた指示そのものが無視される。目安は1ファイル200行以内です。

SECTION 06

第3の選択肢 —「移す」

ここが一番大事なところです。公式の答えは「短くしろ」ではなく「常時ロードから外せ」でした。

何をどこへ読まれるタイミング
手順・チェックリスト・レビュー工程・検証手順skill呼ばれた時だけ
ディレクトリ別・言語別の規約.claude/rules/（paths を書く）該当ファイルを開いた時だけ
毎回必ず起きてほしい挙動・絶対禁止hook / permissions常に（機械的に止まる）
よくある誤解：@import では軽くなりません
分割しても、読み込み先は起動時に全部ロードされます。整理にはなりますが、消費するコンテキストは1バイトも減りません。減らしたいなら skill か rules へ。

SECTION 07

Opus 5 で消すもの、逆に足すもの

公式が名指しで「削除しろ」と書いている指示です。

  • 「最終検証ステップを入れよ」
  • 「サブエージェントで検証せよ」
  • 「答えをダブルチェックせよ」「返答前に再検証せよ」
  • 「考えるな」「推論するな」系のルール（内部タグが漏れやすくなる）
  • 「保守的に」「重大なものだけ報告して」（そのまま従われて報告が減る）
★間違えやすい罠：「検証」でも消していいものと、いけないものがある
例判定
検証指示「最終検証ステップを入れよ」「ダブルチェックせよ」消す
検証仕組みnpm test を実行せよ／bash verify.sh を回せ／Stop hook残す
仕組みとしての検証は、今も公式ベストプラクティスの筆頭項目です（Give Claude a check it can run）。

削るだけだと、別方向に振れます

Opus 5 は既定で返答が長く、作業の実況が多く、サブエージェントに委譲したがります。公式が推奨している文言をそのまま置けます。

Keep responses focused, brief, and concise.
Keep disclaimers and caveats short, and spend most of the response on the main answer.

長い設定ファイルなら、末尾にもう一度置きます。

<tone_preference>Keep outputs reasonably concise.</tone_preference>

SECTION 08

事故を防ぐ4つ

  1. /init を既存ファイルがある状態で叩かない — 既存の CLAUDE.md を上書きした報告があります（特にホームで実行したとき）
  2. バックアップを CLAUDE.local.md にしない — 公式仕様で CLAUDE.md の後に必ず追記ロードされます。新旧の全ルールが同時に読まれ、矛盾を自分で作ることになります
  3. バックアップの置き場も決める — CLAUDE.md.backup が無関係な git add -A で誤コミットされた実例があります。リポジトリ外か .gitignore 済みの場所へ
  4. 巻き戻し機能を過信しない — チェックポイントはツール経由の編集しか記録しません。AIが sed -i や cat > で書き換えたら戻せません。git が本命

SECTION 09

進め方（6ステップ）

  1. git commit で現状を固定（~/.claude は git 外のことが多く、放っておくと版が残りません）
  2. お題を5〜10本決めて、削除前に3〜5回まわして基準値を記録
  3. 本体は触らせず、削除候補と理由と移設先だけ別ファイルに出させる（下のプロンプト）
  4. 人が1件ずつ採否。削除は単独コミット・移設先をメッセージに明記
  5. /clear した別セッションで同じお題を3〜5回。違反率・再指示回数・/context のトークン数を比べる
  6. 違反が1回でも出たら git revert
1回の比較では何も言えません。同じ構成でも2回の測定で5ポイント振れた実測があります。最低3〜5回まわして率で比べてください。
そして、削った本人のセッションに採点させないこと。削除を正当化した推論を抱えたモデルに聞いても、大丈夫としか返ってきません。

合否条件は違反率だけです。行数が減ったことも、体感が良いことも、合格の理由にはなりません。

配布

提案生成プロンプト（そのまま使えます）

本体を触らせず、CLAUDE.md.proposal.md に提案だけ出させるプロンプトです。

私の CLAUDE.md を棚卸ししたい。ただし CLAUDE.md 本体は絶対に編集しないでほしい。
代わりに CLAUDE.md.proposal.md という新しいファイルを作って、そこに提案だけを書いてください。

まず次の3つを読んで、公式が「消せ」と言っているものと「残せ」と言っているものを正確に把握してください。
- https://code.claude.com/docs/en/memory
- https://code.claude.com/docs/en/best-practices
- https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5

そのうえで、私の CLAUDE.md を1行ずつ、次の4分類にかけてください。

A: コードやファイルを読めば分かること（ディレクトリ構成・依存一覧・アーキテクチャ概説）
B: リンタ・テスト・型チェックが既に機械的に強制していること
C: hook や permissions が既に機械的に強制していること
D: 誰も機械的に強制していない、環境固有の事実・禁止・ポリシー・固有名

判定の基準はこれだけです：「この1行が消えたとき、誰が止めるのか」
誰も止めないなら D です。

CLAUDE.md.proposal.md には、次の形式で書いてください。

## 削除を提案する行
| 行 | 引用 | 分類 | 消してよい理由 | 消したあと誰が止めるか |

## 移設を提案する行（消すのではなく置き場所を変える）
| 行 | 引用 | 移設先(skill / .claude/rules / hook) | 理由 |

## 残すべきと判断した行
| 行 | 引用 | 分類 | なぜ残すか |

## 判断できなかった行
| 行 | 引用 | 何が分かれば判断できるか |

守ってほしいこと：
- D に分類したものは、削除提案に入れないでください。移設先が用意できる場合だけ「移設」に入れてください。
- 「たぶん使われていない」で削除提案しないでください。判断材料が無いなら「判断できなかった行」に入れてください。
- @import で分割する案は出さないでください。読み込み先も起動時に全部ロードされるので、コンテキストは減りません。
- 検証やテストを実行するコマンドの記述は、文字列に「検証」が含まれていても削除提案に入れないでください。
  消してよいのは「AIに自己検証を促す指示」であって、「人が回す検証手順」ではありません。
- 要約や圧縮はしないでください。行を短くまとめる提案も不要です。判断だけしてください。
さらに安全にやるなら、本体の編集を機械的に禁止してから回してください。
~/.claude/settings.json の permissions.deny に "Edit(//<絶対パス>/CLAUDE.md)" を足します。絶対パスは // 始まり、 Write(...) ではなく Edit(...) と書きます。
